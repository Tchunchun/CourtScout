## Goal

After a match result is collected, the captain sees how Court Scout's saved
opponent-lineup prediction compared with who actually played. Court Scout
accumulates reproducible evidence for improving later model versions.

## Done when

- [ ] Preparing a scheduled match appends an immutable prediction snapshot
      tied to its stable match ID. The snapshot records its creation time,
      model version, dataset/evidence timestamps, evidence available before
      the match, and the top three opponent scenarios with their confidence,
      players, pairs and courts.
- [ ] Reopening or refreshing preparation never rewrites an earlier snapshot.
      When more than one pre-match snapshot exists, evaluation identifies the
      last prediction the captain saw before the scheduled start. Predictions
      created at or after the match start cannot be selected for evaluation.
- [ ] Once the actual result is collected, the server matches it by stable
      schedule/source identity and derives the opponent's actual players,
      unordered doubles pairs and court assignments. Missing or ambiguous
      results are disclosed and excluded rather than guessed.
- [ ] Each evaluated match reports player inclusion precision/recall, doubles
      pair accuracy, exact court accuracy, top-three coverage and complete
      lineup accuracy. Pair order does not affect the result.
- [ ] The captain can open a Prediction review from the match and see the
      closest saved scenario, the actual lineup, correct players/pairs/courts,
      material misses, the model version and the evidence cutoff.
- [ ] Aggregate evaluation is reproducible by model version and by 0, 1–3,
      4–8 and 9+ earlier matches. It does not automatically change production
      weights; candidate models are promoted through 024/026 only after a
      held-out comparison with the baseline from 022.
- [ ] Match wins, losses and scores are stored with the review for later
      lineup-recommendation research but are not treated as direct labels for
      opponent participation or court prediction.
- [ ] `npm test` passes and the iOS checks in `ios/README.md` pass.

## Notes for the coding agent

- This evaluates the opponent scenarios generated by `analyzeTeam` and shown
  by `buildMatchup`; it is separate from judging whether the captain's chosen
  lineup was the best possible decision.
- Store snapshots and evaluations as workspace documents through `store.mjs`.
  Do not add derived feedback or predictions to canonical `team-data.json`.
- Snapshot the actual response shown to the captain. Reconstructing a past
  prediction with today's model is useful for 022, but it does not prove what
  the captain saw at the time.
- Use time-ordered or team-held-out evaluation. Never tune and report results
  on the same target matches.
- Feature 034 is reserved by the open UTR partner API planning PR, so this is
  035 even though 034 is not yet on main.
