# Lineup Prediction Benchmark Design

Date: 2026-10-29

Status: Implemented by feature 022

## Purpose

Court Scout needs a stable baseline before its opponent-lineup model changes.
The benchmark answers one question: given only the match evidence available at
the time, how accurately would the current model have predicted the team's next
lineup?

The benchmark does not tune the production model. It produces reproducible
measurements that later model versions can compare against.

## Evaluation unit

One sample is one team dataset, one requested number of known matches, and the
next chronological match. The default requested cutoffs are 0, 1, 3, 5 and 8.
A dataset contributes a sample only when it contains a next dated match at that
cutoff.

Matches are ordered by date and then stable match ID. Evidence is stricter than
that ordering: only matches with a date before the target match are visible to
the predictor. An earlier match on the same date is excluded because its result
may not have been known when the target lineup was prepared.

The report records both the requested cutoff and the actual evidence count, so
same-day exclusions remain visible.

## As-of dataset

For every sample, the runner creates a new dataset rather than mutating the
source:

- `matches` contains only evidence matches before the target date;
- roster `qualifyingAppearances` and `sectionalsAppearances` are recomputed
  from those evidence matches;
- season-total eligibility labels are replaced with an unresolved as-of label;
- the original dataset, target match and future matches remain unchanged; and
- the prediction is generated by the existing `analyzeLineupPredictions`
  implementation.

The default eligibility scope is `local`. This measures lineup behavior without
mistaking early-season Nationals qualification thresholds for player
availability. The CLI can run `sectional` or `national` scope explicitly.

Static roster identity, NTRP type and gender are treated as planning context.
The current baseline predictor does not use roster ratings to rank lineup
candidates. A later model that uses time-varying ratings must add rating as-of
handling before it can use this benchmark fairly.

## Metrics

Metrics use the top-ranked scenario unless stated otherwise. Doubles player
order is ignored.

| Metric | Definition |
|---|---|
| Player inclusion precision | Correct predicted players / predicted players |
| Player inclusion recall | Correct predicted players / actual players |
| Doubles-pair accuracy | Actual unordered doubles pairs present anywhere in the prediction / actual doubles pairs |
| Exact-court accuracy | Courts whose predicted player set exactly matches the actual court / actual courts |
| Top-three coverage | Share of matches whose exact complete lineup appears in any of the first three scenarios |
| Complete-lineup accuracy | Share of matches whose top-ranked scenario exactly matches every actual court |

A missing prediction is a miss, not an excluded sample. A match with no usable
actual courts is skipped and disclosed. Aggregate player, pair and court
metrics are micro-averaged from their numerators and denominators. Complete
lineup metrics are averaged per evaluated match.

## Output contract

The JSON report contains:

- report version, model/analysis version, eligibility scope and creation time;
- input dataset IDs and paths;
- one sample per dataset and requested cutoff, including evidence match IDs,
  target ID/date, prediction count, closest scenario and raw metric counts;
- skipped samples with a reason; and
- aggregate metrics overall and by requested cutoff.

JSON is the reproducible artifact. Markdown is a human-readable projection of
the same report. Timestamps are omitted from test comparisons.

## Command line

```sh
node scripts/benchmark-lineups.mjs --input path/to/team-data.json --format markdown
node scripts/benchmark-lineups.mjs --input data/collections --known 0,1,3,5,8 --format json
```

When `--input` names a directory, the runner recursively finds files named
`team-data.json`. Output goes to stdout so callers can redirect it without the
runner managing report storage.

## Model promotion rule

Feature 022 establishes the current-model baseline. Candidate models from 024
and 026 should be promoted only when a held-out comparison shows:

1. at least a 15 percentage-point improvement in top-three coverage for the
   0, 1 and 3-match cutoffs combined;
2. no more than a 2 percentage-point decline in established-season exact-court
   accuracy;
3. no future-match or same-day-result leakage; and
4. no invalid lineup generation.

The owner must accept or revise these thresholds before a new model becomes the
default.

## Limitations

One season dataset cannot measure a true zero-match cold-start model because
the current predictor needs observed court history. It will correctly report no
prediction and zero recall at that cutoff. Cross-season evidence enters only
after feature 023 provides confirmed history links.

The benchmark evaluates opponent lineup prediction. It does not decide whether
the captain's own chosen lineup was optimal; match scores can support that
separate question later.
